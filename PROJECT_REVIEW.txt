1. EXECUTIVE SUMMARY
================================================================================

The NZ Lotto Powerball Wheel Analysis & Prediction Platform is a comprehensive
Python application for analysing, predicting, backtesting, and generating
tickets for NZ Lotto Powerball (6/40 + Bonus 1-40 + PB 1-10). The platform
consists of ~45 Python modules, a 20-page Streamlit dashboard, a 25-endpoint
FastAPI server, and 7 CLI commands.

Overall assessment: The codebase is well-structured, feature-rich, and
functional. Core algorithms (Bayesian prediction, GA optimisation, Bluskov
wheel validation) are correct. The dashboard is polished with responsive
layout, Plotly charts, and session-state persistence. Documentation is
thorough.

Key strengths:
  - Comprehensive prediction suite (7 methods + ensemble)
  - Robust backtesting with bootstrap CI and paired t-tests
  - Production-grade data pipeline with fallback chain
  - 20-page interactive Streamlit dashboard
  - Full FastAPI with Swagger docs
  - Well-documented code with 100% docstring coverage on new modules

Key issues found and fixed during review:
  - Database schema mismatch (lotto.db vs lotto_working.db)
  - Missing bonus column in working database
  - Unicode histogram character breaking on Windows console
  - avg_prize_without division bug in backtest

4. BUG FIXES APPLIED
================================================================================

4.1 [CRITICAL] Database Schema Unification
    Problem: update_draws.py wrote to lotto_working.db with n1..n6 columns;
             all other modules read lotto.db with comma-separated numbers column.
    Fix: Unified all modules to use lotto.db with numbers TEXT column.
    Files: update_draws.py, lotto_wheels.py, rotation_scheduler.py

4.2 [CRITICAL] Missing Bonus Column
    Problem: init_working_db() created the draws table without a bonus column,
             causing KeyError in load_draws() and 18 test failures.
    Fix: Added bonus INTEGER CHECK (bonus BETWEEN 1 AND 40) to schema.
    Files: lotto_wheels.py

4.3 [MEDIUM] Unicode Histogram on Windows
    Problem: backtest.py used █ (U+2588) for histograms, which fails on
             Windows cp1252 consoles with UnicodeEncodeError.
    Fix: Replaced █ with # for cross-platform compatibility.
    Files: backtest.py

4.4 [LOW] avg_prize_without Division Bug
    Problem: avg_prize_without was computed as total_prize_without/upgrade_count
             instead of total_prize_without/num_sims, inflating the value.
    Fix: Corrected to divide by num_sims.
    Files: backtest.py (already fixed in current codebase)

5. REMAINING ISSUES
================================================================================

5.1 [MEDIUM] Duplicate Module: database.py and db_schema.py
    Both files contain identical code (245 lines each). This is confusing and
    creates a maintenance burden. One should be removed, and all imports
    should reference the remaining file.
    Recommendation: Delete db_schema.py, keep database.py.

5.2 [MEDIUM] BOM Characters in Several Files
    Files with U+FEFF (BOM) at line 1:
      - main.py
      - pipeline.py
      - config/quantum_features.py
      - steps/bayesian_fusion.py (and several other steps/*.py)
    These appear to be encoded as UTF-8-BOM but some contain non-UTF-8 bytes.
    Recommendation: Convert all files to UTF-8 without BOM.

5.3 [MEDIUM] Non-UTF-8 Encoded Files
    steps/bayesian_fusion.py, steps/redundancy.py, and others contain bytes
    that cannot be decoded as UTF-8 (e.g., 0x96 in position 3701). These files
    fail ast.parse() and will break any tool that reads them.
    Recommendation: Convert to UTF-8 or fix encoding.

5.4 [LOW] GA Optimisation Timeout
    The GA uses 50,000 EV simulations per individual, making it extremely slow.
    For 5 pop * 10 gens = 2.5M simulations. Even with caching, this is
    impractical for interactive use.
    Recommendation: Add a --quick flag using 5,000 sims; cache per-draw
    prize lookups; use vectorised numpy where possible.

5.5 [LOW] No Database Migration System
    Schema changes require manual coordination. No Alembic/SQLAlchemy migrations.
    Recommendation: Consider adding alembic for future schema evolution.

5.6 [LOW] Missing Rate Limiting on API Calls
    update_draws.py and crawler.py make external HTTP requests but don't track
    rate limits beyond polite delays.
    Recommendation: Track request timestamps and enforce minimum intervals.

7. PERFORMANCE ANALYSIS
================================================================================

7.1 Bottlenecks
    - simulate_bonus_ev() with 1M sims: ~10-20s per wheel, O(n_sims * n_tickets)
    - GA optimisation: 50k sims * pop * gens, impractically slow
    - HierarchicalBonusPredictor: O(draws) per fit, acceptable (<1s for 1000 draws)
    - Co-occurrence matrix: O(draws * C(6,2)) for triplets, acceptable

7.2 Already Optimised
    - backtest.py uses np.bincount for histogram aggregation (not per-draw loops)
    - wheel_generator.py sorts coverage by size for early-exit greedy
    - dashboard uses @st.cache_data(ttl=3600) for expensive computations

7.3 Recommendations
    - Add simulate_bonus_ev parallelisation (multiprocessing across tickets)
    - Pre-compute prize lookup table once and reuse across GA generations
    - Use numba for the bottleneck loop in the EV simulation
